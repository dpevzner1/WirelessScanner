## 2. Source-of-truth order

When documents disagree, trust them in this order:
1. Code and passing tests
2. `config/pipeline/wirelessscanner-remediation-control.json` (findings, tasks, iterations, hash-chained events)
3. `docs/STATUS.md` (feature and requirement status)
4. Feature documentation (`README.md`, `docs/USER_GUIDE.md`, `docs/TECHNICAL_REFERENCE.md`, `docs/SATURATION_TEST_SPEC.md`)
5. `PLAN/` (the original May 2026 design baseline; historical)

Fixing a disagreement is a task. Record it as a finding; don't silently edit it away.

## 3. Evidence labels

Every status claim uses exactly one of these labels (from the engine's `LessonsLearned/ITERATIVE_DOCUMENTATION_STANDARD.md`):
- **Validated** — exercised by an automated test or recorded harness
- **Observed** — measured or seen during a run, but not under an approved test
- **Designed** — implemented or documented, awaiting the target environment, hardware, review or approval
- **Blocked** — fails closed because required evidence or authority does not exist

Never write "complete" or "done" without one of these labels.

Requirements that were never built are marked **Not implemented** in `docs/STATUS.md`, with a backlog note. That is a scope state, not an evidence label, and it is never relabelled as Designed.

## 4. The breadcrumb trail (what was done, tested, passed or failed)

| Artifact | Path | Updated when |
| --- | --- | --- |
| Remediation control (v2) | `config/pipeline/wirelessscanner-remediation-control.json` | At every checkpoint (§6): findings, tasks, work packages, iterations (hypothesis → change → test → outcome) and hash-chained events |
| Lesson records | `LessonsLearned/records/*.md`, registered in `LessonsLearned/lesson-register.json` | For each task or iteration, and whenever something fails, is aborted or resumes. Failed attempts are never deleted |
| Decision records | `docs/decisions/DR-*.md` | For every architecture, policy or UX decision. Superseded decisions stay, marked superseded |
| Review attestation ledgers | `governance/reviews/<RV-ID>/ATTESTATION-LEDGER.jsonl` | Every review, verification or test run that the control cites. Commands go through `tools/review_attestation.py run`. The ledger is sealed at the end |
| Evidence files | `governance/evidence/**` | Each is captured once and hashed into the control file. A new capture gets a new evidence ID |
| Engine consultation log | `docs/consultation/ENGINE_CONSULTATION_LOG.md` (+ raw query output in `governance/evidence/consultation/`) | Every consultation |
| Changelog | `CHANGELOG.md` | Every user-visible change |
| Status matrix | `docs/STATUS.md` | Whenever a feature's evidence label changes |

## 5. DevOps engine consultation protocol

1. **Read-only.** Use only `source_index_engine.py query`, and read files under `GPT OUTPUT/`, `Source/`, `docs/` and `LessonsLearned/`. Never run the engine's ingestion, build, export, harness or runner commands; never write inside the engine folder; never start its services. Set `PYTHONDONTWRITEBYTECODE=1`.
2. **When to consult.** At design time for any new feature, UX change, architecture or security decision; before acceptance criteria are finalised; and when a test strategy is defined.
3. **How to record.** Add a `C-nn` row to the consultation log: the question, the engine material with paths and pages, the result, and how it was applied. Save raw query output under `governance/evidence/consultation/`. Decision records cite the consultation IDs.
4. **Limits.** Index hits are pointers, not proof of competence. Record gaps (e.g. C-01: no RF/Wi‑Fi coverage) instead of filling them with invented engine authority.
5. **Conflicts.** If engine guidance conflicts with the code or a requirement, record a finding and a decision; the owner decides.

## 6. Mandatory checkpoints (from the engine's remediation standard)

1. Before starting a task: confirm its scope, dependencies and acceptance in the control file.
2. Before rerunning a test: check earlier fingerprints. An unchanged rerun needs a written justification.
3. After each material change or failure: record an iteration, evidence and an event.
4. Before task closure: verification evidence, regression evidence and a lesson record must be linked.
5. Before qualification: an independent reviewer is required. Until one is assigned, qualification stays `not_qualified`.

## 9. Keeping documentation current
A change is not finished until:
1. the code and tests are updated;
2. `docs/STATUS.md`, `CHANGELOG.md` and the affected feature docs are updated;
3. the control file has an iteration and an event, and a lesson record exists or has been updated;
4. `tools/sync_github_export.py` has been run and its `--check` reports no differences.
