## Owner request and decisions
**Request.** Build an Android APK in `/AndroidApp`:
- **every feature ported one for one**;
- the tablet's own Wi‑Fi hardware integrated;
- reports (PDF/CSV/JSON) sendable by email or storable in any installed cloud app.

**Owner choices (2026-10-19):**
1. **Stack:** native **Kotlin and Jetpack Compose**, like the references. Analytics are re-implemented in Kotlin and **proven identical to Windows with shared known-answer fixtures** generated by the C# code.
2. **Scan limit:**
   - Android 9+ allows 4 app scans per 2 minutes unless *Wi‑Fi scan throttling* is turned off in Developer options.
   - **Detect, guide and fall back.** The app detects throttling and explains how to turn it off for full-rate tests (the 5 s cadence, as on Windows). Otherwise it runs at the allowed rate, and the effective rate is printed on every report.
3. **Scope:**
   - **REST API on the tablet:** localhost by default, local network opt-in, same endpoints and `X-API-Key`.
   - **Responder role on the tablet:** optional, in addition to the client.
4. **Testing:**
   - The **owner sideloads** the APK.
   - Automated JVM tests and the existing API 36 tablet emulator are used here.
   - An in-app **diagnostics export** (redacted) replaces device logs.

## Architecture
```
AndroidApp/
├── core/   pure Kotlin/JVM library, no Android dependency
│           (domain records, ChannelMath, SpectrumLayout, SaturationAnalyzer,
│           PhysicalUnitGrouper, NetworkSelection, ConnectionAnalyzer, report model,
│           CSV/JSON writers, responder protocol client + server)
│           JVM unit tests + parity fixtures from the C# implementation
└── app/    Android application
            (Wi‑Fi platform layer, probes, storage, foreground service,
            Compose UI, PDF rendering, Sharesheet / SAF export, REST server, diagnostics)
```
- **No third-party SDKs for cloud or email.** "Share or send" uses the Android Sharesheet + `FileProvider`. "Save a copy" uses `ACTION_CREATE_DOCUMENT` (Storage Access Framework), which lists Drive, OneDrive, Dropbox and any other installed provider (A-LRN-004 / 005 / 036).
- **One frozen report snapshot** renders PDF, CSV and JSON (A-LRN-010). The CSV bundle is shared as one ZIP or as separate files.
- **Storage:** platform SQLite (`SQLiteOpenHelper`), with no annotation processing. Settings in `SharedPreferences`; secrets (API key, responder key) encrypted with the Android Keystore.
- **Long tests:** a foreground service (type `location`) with a partial wake lock. Lifecycle handled as A-LRN-035 / 044 (configuration changes are not departures).

## Platform mapping (Windows → Android)
| Windows capability | Android equivalent | Difference stated in the app and reports |
| --- | --- | --- |
| `WlanScan` + scan-complete notification; fresh / stale / failed cycles | `WifiManager.startScan()` + `SCAN_RESULTS_AVAILABLE_ACTION` with `EXTRA_RESULTS_UPDATED` (true = fresh, false = cached / stale); a refused `startScan` = throttled | Throttling: 4 scans / 2 min unless Developer option off |
| RSSI, channel, centre frequency, width, PHY, beacon interval, security | `ScanResult.level`, `frequency`, `centerFreq0/1`, `channelWidth`, `getWifiStandard()` (API 30), `capabilities`; information elements (API 30) | Beacon interval not exposed → "not reported" |
| Beacon age | `SystemClock.elapsedRealtime` − `ScanResult.timestamp` (µs since boot when last seen) | Same meaning |
| BSS Load, WPS identity, RNR, Multiple-BSSID | `ScanResult.getInformationElements()` (API 30), same parsers as Windows | Android 10 and older: "not reported" |
| **TSF radio clock (physical-unit evidence)** | **Not exposed by Android** | Grouping uses WPS UUID, MAC family and Wi‑Fi 7 MLD address (`apMldMacAddress`, API 33). Same-radio evidence is unavailable, so confidence is lower and labelled |
| Current connection (SSID, BSSID, PHY, rates, signal) | `NetworkCapabilities.transportInfo` as `WifiInfo` (location flag), `getRx/TxLinkSpeedMbps` | — |
| Driver frame counters (retries, FCS) | No public API | "Not reported by Android" |
| Interface byte counters | `TrafficStats` totals | Whole-device traffic (Wi‑Fi-only tablet ≈ Wi‑Fi) |
| ICMP with source address (`IcmpSendEcho2Ex`) | System `ping` (`-I wlan0`, `-t <ttl>`), parsed | Millisecond resolution from `ping`; TCP stays the primary internet metric, as on Windows |
| TCP / DNS / HTTPS bound to Wi‑Fi | `Network.bindSocket` / `Network.socketFactory` / `Network.openConnection` for the Wi‑Fi `Network` | — |
| Windows Location (DETECT) | `LocationManager` (GPS / network providers; no Play services) | — |
| Keep PC awake | Foreground service + partial wake lock | Visible notification while a test runs |
| REST API (`HttpListener`, localhost) | Embedded HTTP/1.1 server, localhost by default, LAN opt-in | — |
| LAN responder (`WirelessScanner.Responder`) | Same WSR1 protocol in Kotlin (client and optional server role), byte-compatible | Interoperability tested against the C# responder |
| DPAPI-protected secrets | Android Keystore (AES-GCM) | — |
| Installer: update, repair, uninstall, registry, icon | APK install/update (versionCode), launcher icon from `branding/android` | Repair and registry not applicable |
| Exports to files (Save dialogs) | **Share or send** (email, chat, cloud apps via the Sharesheet) and **Save a copy** (any document provider via SAF) | Provider list depends on the tablet (A-LRN-005) |

## User experience
The touch UX is specified in [`AndroidApp/docs/UX_SPEC.md`](../../AndroidApp/docs/UX_SPEC.md) (consultation C-11). Summary:
- **Expanded (tablet landscape):** the same three panes as Windows, plus a navigation rail.
- **Medium:** the explorer becomes a side sheet and the mode panel a bottom sheet.
- **Compact:** tabs.
- **Same names, order, status words and colours as Windows.**
- **Touch:** targets of at least 48 dp; long-press and visible ⓘ / ⋮ buttons replace hover and right-click.

## Addendum 2026-10-19: device and deployment gate (lesson LL-2026-10-19-ANDROID-DEVICE-AUTH)
The first preview build was copied to the owner's tablet while `adb` reported it as `unauthorized`. The reference projects had already recorded this exact failure on this tablet, and its fix, but the intake for this decision carried over only their architecture and export lessons. It did not carry over their device and deployment lessons. These lessons now apply:

| Reference lesson | Rule for this port |
| --- | --- |
| A-LRN-043 (breathwork) | A USB-connected device is not an authorized test target. `adb devices` must show `device` before any install, launch, visual or log evidence |
| A-LRN-016 (breathwork) | Emulator acceleration, AVD state and ADB readiness are separate gates; probe before relying on them |
| A-LRN-017 (breathwork) | All device evidence is bound to the exact APK SHA-256, package, version, device and API |
| Playbook §1 / §10 (MobileApp) | Authorize the tablet at the start of every session, before coding; the authorization reset between sessions |
| Playbook §6 (MobileApp) | `adb install` installs; `adb push` and MTP only copy. MTP success is not proof. "Problem parsing the package": compare size and SHA-256, the PK header and `minSdk` |
| R3 §5 (MobileApp) | The working fix for `unauthorized`: on the tablet, unlock, revoke or toggle USB debugging, replug, then "Always allow". `adb kill-server` alone does not fix it |

**Correction.** The parity matrix (row D2) and the session summary described A-LRN-043 as "device evidence bound to APK hash". That is A-LRN-017; A-LRN-043 is the device-authorization rule above.

**Gate.** [`tools/android_deploy.ps1`](../../tools/android_deploy.ps1):
- `-PreflightOnly` runs at the start of every Android session;
- deploy copies to `SD card\DEPLOY` with a read-back SHA-256 check;
- `-Install` runs only on an authorized target.

Procedure: [`AndroidApp/docs/DEPLOYMENT.md`](../../AndroidApp/docs/DEPLOYMENT.md).

## Addendum 2026-10-19 (b): scan throttling measured; two-way parity
- **Scan throttling.** The rule (4 foreground scans per 2 minutes) was measured on the tablet.
  - No permission, install-time grant or `Settings.Global` write lifts it on Android 14.
  - The supported fix is the owner's developer option.
  - Reference: [`AndroidApp/docs/WIFI_SCAN_THROTTLING.md`](../../AndroidApp/docs/WIFI_SCAN_THROTTLING.md); lesson LL-2026-10-19-ANDROID-SCAN-THROTTLING; finding F33, task T30.
- **Two-way parity.** From now on, every change to either app is carried to the other with its own layout adaptation, or recorded as a platform limit or exception. This is a hard control: [DR-0017](DR-0017-two-way-platform-parity.md); finding F34, task T31.

## Acceptance
- **Analytics parity.** Golden fixtures from the C# code (saturation, units, connection, channel math, spectrum layout) produce identical numbers in Kotlin.
- **Exports.** Every report format renders from one snapshot. Share and Save are tested, including cancelled and empty choosers.
- **Wi‑Fi on the tablet.** Scans, connection info and probes run on a real tablet: the owner's sideload, with a diagnostics export returned.
- **Responder interoperability.** The Kotlin client works against the C# responder, and the C# client against the Kotlin responder.
- **No regression.** No Windows behaviour changes. The Android code lives only under `AndroidApp/`.
